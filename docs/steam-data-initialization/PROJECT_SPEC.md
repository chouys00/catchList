# Steam 大量資料初始化流程規格

## 背景與目標

現有 `steam_discovery` 每月更新會用 Steam 搜尋頁定位月份，再依序讀取 `appdetails` 與商店頁面。這套流程適合每月少量補資料，不適合一次建立 2015 年 1 月至 2026 年 2 月的大量歷史清單。

本專案新增獨立的初始化流程。流程先從 FronkonGames 資料集取得大量遊戲，完成第一輪篩選後，每個候選遊戲各讀一次 `https://store.steampowered.com/app/{appid}` 補齊商店欄位。全球全語系終身評價與評論數由 FronkonGames 的 `positive`／`negative` 支撐；是否另加官方 Steam Reviews API 仍未決定。

初始化流程不得改變既有每月更新的命令、資料來源與輸出行為。

## 使用情境

- 第一次建立 2015-01 至 2026-02 的遊戲資料。
- 網路中斷或 Steam 限流後，從本機進度繼續，不重抓已成功的頁面。
- 檢視候選遊戲、排除原因與無法判定的資料，再決定是否重試。
- 驗證初始化結果後，另行決定是否搬移到正式報告；本專案不直接寫入雲端報告。

## 範圍

### 需求

- `REQ-001`：新增獨立初始化命令，處理 2015-01 至 2026-02；日期上下限可由命令列指定。
- `REQ-002`：初始化流程以 FronkonGames 為主要大量資料來源，固定並記錄資料版本、下載來源、檔案雜湊與載入時間。
- `REQ-003`：第一輪門檻使用全語系 `positive` 與 `negative`：`positive / (positive + negative) * 100 >= 85`，且評論總數大於 500。判斷使用未四捨五入的比率，顯示時才取整數。
- `REQ-004`：`positive + negative = 0` 或欄位異常時，不視為未達門檻；寫入缺失清單，等候另一次補查。
- `REQ-005`：第一輪同時檢查 `genres`、`categories` 與 `tags`，排除大型多人線上、免費遊玩、軟體、MMORPG、MOBA、PvP 等已明確禁止的項目。
- `REQ-006`：第一輪通過後，每個 AppID 只請求一次 `store.steampowered.com/app/{appid}`。初始化執行期不得呼叫 `search/results`、`api/appdetails` 或其他 Steam 資料 API。
- `REQ-007`：商店頁面應解析發行時間、社群標籤、中文名稱、免費狀態、內購、MMO、VR、支援語言與搶先體驗；全球全語系終身好評率與評論數沿用 FronkonGames。
- `REQ-008`：第二輪使用商店頁面的最新排除訊號，並沿用第一輪已固定來源的好評率與評論數；排除內購、MMO、僅限 VR、免費遊玩、軟體、MMORPG、MOBA 與 PvP。
- `REQ-009`：遊戲分類以商店頁面的社群標籤為主；Steam 功能分類與 FronkonGames 的 `tags`、`categories`、`genres` 依序作為補充。能取得穩定 ID 時優先用 ID，文字別名只作備援。
- `REQ-010`：商店頁面缺欄位、年齡驗證、地區限制、下架、版面變動或解析失敗時依重試規則處理；不確定的硬性排除欄位維持 `unknown`，不可預設為安全。
- `REQ-011`：頁面回應與解析結果須快取，可安全中斷續跑；解析器版本變更時，可只重新解析既有回應，不必重新請求。
- `REQ-012`：輸出採原子寫入，固定放在 `steam_discovery/preview/initialization/`，不得覆蓋既有月份預覽或雲端 `遊戲.md`。
- `REQ-013`：初始化報告須保留 AppID、中文名稱、發行時間、全語系好評率、評論數、社群標籤、類型與單一中文支援狀態。繁體中文或簡體中文任一成立，就記為「支援中文」，不分開記錄或顯示語系。
- `REQ-014`：每筆候選資料都要有可追查的最後狀態：通過、第一輪排除、第二輪排除、待重試或資料缺失，並記錄原因。
- `REQ-015`：既有 `npm run update:games`、根目錄 `npm run update:all` 與排程檔的行為、輸出位置及篩選規則保持不變。

### 非目標

- 不重寫現有每月更新流程。
- 不在初始化流程呼叫 Steam 搜尋結果、`appdetails` 或 Steam Reviews API；是否增加後者留待獨立決策。
- 不保證為沒有官方中文譯名的遊戲自行翻譯名稱；若商店僅顯示英文名稱，保留原名並標記無本地化名稱。
- 不抓臺灣售價、遊戲簡介、Steam 評價文字、純 PvP 模式細節、手把支援、每筆資料抓取時間或是否仍在販售。
- 不在本計畫內搬移、合併或覆蓋雲端 `遊戲.md`。
- 不在規劃階段直接執行 2015-01 至 2026-02 的完整抓取。

## 資料來源與欄位優先順序

| 欄位 | 第一輪 | 第二輪／最終值 | 缺失處理 |
|---|---|---|---|
| AppID | FronkonGames | 商店網址一致性檢查 | 無效即排除並記錄 |
| 發行時間 | FronkonGames | 商店頁面 | 無法解析則待重試 |
| 中文名稱 | 無 | 商店頁面繁中介面 | 沒有本地化名稱時保留原名 |
| 好評率、評論數 | FronkonGames `positive`／`negative` | 固定資料集值 | `0/0` 或欄位異常列資料缺失，不以商店頁中文或最近評價替代 |
| 社群標籤 | FronkonGames `tags` | 商店頁面 | 缺失時待重試，不猜測硬性排除條件 |
| 類型 | `genres`、`categories`、`tags` | 社群標籤為主，其他欄位補充 | 保存來源與判定原因 |
| 支援語言 | FronkonGames | 商店頁面語言表 | 保存未知狀態 |
| 免費、內購、MMO、僅限 VR、搶先體驗 | 可做初篩 | 商店頁面 | 無法判定時待重試；不以 `price = 0` 單獨判定免費 |

## 核心規則

### 評論口徑

使用全球全部語言、終身累積的正評率與評論數。商店介面語言設為繁體中文，不代表可以使用「您的語言」評論。最近 30 天的全語系評價也不能替代終身評價。

FronkonGames 的 `positive`／`negative` 是全球全語系終身累積的實用篩選資料。使用者已實測多款正常收錄且遠離門檻的遊戲，數值與同日 SteamSpy 一致。資料集不必保證每筆即時同步；`0/0`、異常與門檻附近資料仍要列出，以便日後決定是否另開複核工作。最近 30 天或目前語言評價一律不得替代 FronkonGames。

### 排除規則

硬性排除條件需集中定義、保留命中來源並有測試案例。`PvP` 依本次需求視為排除條件，即使遊戲只是附帶 PvP 也會被排除。VR 規則沿用先前需求，排除「僅限 VR」，可選 VR 模式不因此排除。內購包含頁面明確標示的遊戲內購買。

### 未知狀態

初始化執行期會區分不同的未知狀態。網路或解析失敗先重試；評論或硬性排除欄位仍無法確認時，保留原始失敗原因並列為待確認，不得預設通過。

## 品質與相容性

- 相同資料集、相同商店頁面快取與相同設定應產生相同結果。
- 不因重跑產生重複月份或重複 AppID。
- HTTP 429、5xx、逾時與暫時網路錯誤採有上限的退避重試，遵守 `Retry-After`。
- 商店頁面解析器以保存的 HTML 樣本測試，不把脆弱的單一正規表示式當作唯一依據。
- 正常頁面、年齡驗證頁、免費遊戲、內購、MMO、僅限 VR、搶先體驗、下架／地區不可用及沒有中文名稱都要有固定測試案例。
- 初始化模組與每月更新模組分開；若抽出共用程式，需先以回歸測試證明每月更新結果不變。

## 安全與資料邊界

- 只寫入專案內的初始化預覽與快取資料夾。
- 不寫入 `G:/我的雲端硬碟/CatchList/遊戲.md`。
- 不刪除或覆蓋既有 `steam_discovery/preview/` 內容。
- 資料集下載、商店頁面抓取與完整歷史執行都應明確顯示來源、範圍與進度。
- 完整執行可花數十分鐘以上；以每筆間隔 1.5 秒估算，1,000 筆光固定等待就約 25 分鐘，尚未包含限流與重試。

## 成功條件

- A1 證明 FronkonGames 可作為全球全語系終身評價與評論數的篩選來源，且商店頁不會誤用最近或目前語言評價。
- 能以固定版本的 FronkonGames 資料重現第一輪候選清單。
- 能在中斷後續跑，且每個候選 AppID 都有明確結果或待處理原因。
- 完整範圍輸出只出現在專用初始化預覽資料夾。
- 現有每月更新測試與初始化測試全數通過，既有命令未被初始化流程接管。

## 已知限制與待驗證事項

- FronkonGames 既有 AppID 預設不會重新抓取，單筆資料新鮮度不明；不能把資料集評論數當成最新值。
- FronkonGames 會在免費與缺少價格資料時都寫入 `price = 0`，因此不能直接判定免費遊玩。
- Steam 商店 HTML 沒有穩定的公開資料契約，版面、Cookie、年齡驗證與地區狀態都可能改變內容。
- 繁中商店頁沒有可靠的全語系終身評價，故不得作為該欄位來源；這不影響 FronkonGames 初篩。
- 商店頁面的內購、VR 與 MMO 標記可能沒有一致的文字或屬性，A1 必須先找出可靠訊號與失敗判定。
- 社群標籤由使用者產生，會隨時間與顯示語言改變；規則需保存原始值與正規化後的值。
